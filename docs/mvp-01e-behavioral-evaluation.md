# MVP-01E — Local End-to-End Behavioral Evaluation

This is an **evaluation harness, not a production agent subsystem**. It uses
the merged v2.5.1 Conversation Manager, Ollama Model Gateway, existing
PostgreSQL domain state, authorized workers, and MVP-01A–D response routing.

One foreground invocation creates a unique database, applies every ordered
migration, provisions **one synthetic user and selected persona**, executes
28 predetermined messages over three conversations (including process-host
reinitialization), records state **after each reply and worker checkpoint**,
writes a self-contained ZIP, and drops **only its own newly created database**.
No production data, schema resets, hidden test domain approvals or new
scheduler are introduced.

## 1. Prerequisites

Python 3.11+, Docker with Compose, and a locally running Ollama server.
A model capable of natural conversation is recommended; the much smaller
model used by CI is a useful protocol smoke test, not a conversational-quality
benchmark.

```bash
git clone https://github.com/BetrayedByEthanol/Chatbot.git
cd Chatbot
python -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[test]"
ollama pull qwen2.5:7b
```

## 2. Isolated database and environment

Copy `.env.e2e.example` to `.env.e2e` and replace the placeholder password.
**Never commit the populated file.** Either source it or set the exported
variables directly in your shell; the script does not load dotenv packages.

```bash
cp .env.e2e.example .env.e2e
# Edit .env.e2e with a unique local-only password (both occurrences match)
source .env.e2e
docker compose -f compose.e2e.yaml -p persona-e2e-mvp01 up -d --wait
```

**Optional single-command execution:** Once `.env.e2e` is configured,
you can replace the separate Compose startup, Python invocation and
Compose shutdown commands below with:

```bash
bash scripts/run_persona_e2e.sh --report artifacts/mvp01e-review.zip
```

This wrapper creates an invocation-unique Compose project, starts isolated
PostgreSQL, and passes a fresh private `--publication-status-file` path to
the runner. The runner atomically writes `PUBLISHED` **only after** ZIP
publication succeeds, before dropping its generated database. The wrapper
removes the Compose project and volumes **only when this signal exists**;
a nonzero exit from failed scenario assertions still cleans up when the
diagnostic ZIP was successfully written.

If ZIP publication fails (unwritable destination, full disk, interruption,
or failed publication-status write), the marker is absent, and the wrapper
**preserves the Compose service and PostgreSQL volume** for recovery. It
prints the unique Compose project name and manual inspection/cleanup commands.
Do not run `down -v` until the evidence is recovered:

```bash
docker compose -f compose.e2e.yaml -p <printed-project-name> ps
# Inspect/recover the retained database; then, only when safe:
docker compose -f compose.e2e.yaml -p <printed-project-name> down -v
```

The wrapper rejects `--keep-db` and caller-supplied
`--publication-status-file` to protect the cleanup protocol. For debugging,
use the direct Python CLI and manual Compose lifecycle. Unknown publication
status is treated as **not safe to delete**, even if the runner exits zero.

PostgreSQL 16 binds only to `127.0.0.1:55433` by default. The runner
requires an administrative DSN that connects to this **isolated server's**
`postgres` maintenance database. Do not use a production cluster, even
when connecting to its maintenance database.

## 3. One-command run and cleanup

```bash
python scripts/persona_e2e.py \
  --scenario scenarios/mvp01e_conversation.json \
  --model qwen2.5:7b \
  --report artifacts/mvp01e-review.zip
```

The script creates a random `persona_e2e_<16-hex-digits>` database, applies
migrations, runs the scenario and writes the ZIP **before** deletion.
Default cleanup drops *only* the database generated by this invocation.
Report paths must be new and end in `.zip`; no existing report is overwritten.
No manual `DROP DATABASE` command is needed. The Docker service itself
remains available for another run; stop its isolated stack when finished:

```bash
docker compose -f compose.e2e.yaml -p persona-e2e-mvp01 down -v
```

For debugging, pass `--keep-db`. The runner prints the generated DB name
and preserves it; it never drops a database by arbitrary user-supplied name.
When a setup or conversation step fails, it still writes a partial diagnostic
ZIP and then cleans up the generated database. If the ZIP cannot be saved **or
its publication marker cannot be written**, both database cleanup and wrapper
Compose teardown are skipped to preserve evidence. The marker is internal
to the wrapper and does not appear inside the ZIP.

Exit status 0 = deterministic contract checks passed; 1 = observed failures
or scenario exceptions; 2 = cleanup failure. Publication errors raise a
nonzero error, with the database and Compose stack retained by default.
A nonzero exit does **not** determine whether evidence was published:
the private marker is the only cleanup authorization. Conversational quality is
**always human-review pending**, regardless of exit status. If setup fails
before a database was created, no DB is dropped.

## 4. Scenario coverage

`scenarios/mvp01e_conversation.json` covers ordinary greetings, reported
daily events, an implicit exercise objective, corrections and clarifications,
topic switching, a same-conversation host restart, explicit clock and
asynchronous text-statistics requests, Nginx procedural help, a request to
execute a command that the system has **not** been authorized to execute,
a cross-session goal reference, obstacles, preferences and a hypothetical.

The input text is fixed, but assistant responses are **not fabricated or
scripted**. The scenario deliberately does not rewrite user input based on a
model answer. Later rounds can add separately versioned conditional scenarios.
Failures of cross-session personal recall, natural goal approval, or adaptive
cognition are recorded, but not mislabeled as MVP-01 contract failures because
these belong to MVP-02/03/04.

## 5. Evidence in the ZIP

- `manifest.json`: source Git commit, model, Python/OS versions, migration
  SHA-256 fingerprints, and execution metadata (never DB credentials).
- `scenario.json` and `transcript.json`: exact synthetic user turns,
  model/tool replies, IDs, sessions, restart and follow-up evidence.
- `state_snapshots.json`: application dialogue state, turn trace and
  global domain counts; read-only, user/persona-scoped PostgreSQL rows from
  a fixed allowlist (conversation, intent, dialogue, memory, goals, cognition,
  emotion, relationships, tools, operations and events). Captures before
  and after registered tool and explicit-memory worker ticks. Queries run
  with PostgreSQL `REPEATABLE READ READ ONLY`; no cross-tenant export.
  Each table has its total count and `truncated` flag if over 500 rows.
- `model_requests.json`: the **outbound Ollama JSON request**
  recorded in `OllamaChatGateway._chat()` *after* all gateway augmentation.
  Includes structured-mode `format=json`, the exact inserted intent-extraction
  system instruction, selected model, stream setting, and complete sent
  messages. `capture_boundary=ollama.outbound` identifies this evidence;
  deterministic test gateways are explicitly marked
  `pre_gateway_unverified` and are not claimed to show the outbound prompt.
  Observers receive detached copies and cannot modify the sent request.
  Review missing references at context construction vs. gateway augmentation.
- `delivery_events.json`: real host output and late tool follow-ups.
- `evaluation.json`: per-turn deterministic checks for persisted/delivered
  responses, expected registered tool/intent signals where unambiguous,
  authorized Goal isolation and asynchronous follow-up completion.
- `errors.json`: first failed step and bounded exception evidence.
  A model inference failure after authenticated ingress adds a
  `message_failed` transcript entry correlated using the persisted
  idempotency receipt. `after_failed_turn` captures its committed
  user input, intent signals, dialogue state, turn trace and durable events
  before database teardown. If observation itself fails, that secondary
  error is recorded **after** the original failure, without replacing it.
  Ingress failures without a committed receipt are labeled
  `ingress_committed=false`; no phantom turn is invented.

Some application observations and SQL table snapshots are taken in separate
transactions; each SQL-table group is internally consistent, but the entire
bundle is **not** one global atomic snapshot. The runner operates sequentially
to make these observations meaningful. The tests do not auto-grade
understanding, emotional appropriateness, strategic competence or natural
conversation quality.

**Privacy:** Generated reports contain full synthetic conversations, model
prompts and domain state. Do not replace the scenario with real user data
before sharing a ZIP. Review files before uploading.

## 6. Repository regression test

Existing integration-test setup applies migrations to a disposable
`TEST_DATABASE_URL`. The new tests reuse it without creating or deleting
databases and exercise the real host, PostgreSQL state snapshots, model
fallback, worker follow-ups, ZIP contents, failed runs and tenant isolation:

```bash
python -m pytest -q tests/test_mvp01e_behavioral_evaluation.py
```

The repository's full PostgreSQL suite and live-Ollama job remain required
PR gates. They cannot certify natural-language understanding by themselves.

## 7. Review workflow

Upload `artifacts/mvp01e-review.zip` into this project's conversation.
Review each turn as **input → admitted signal → dialogue state → actual model
context → response → subsequent state/worker outcome**. Classify mismatches
by Conversation interpretation, context/retrieval, model behavior, dialogue
progress, tool admission/execution, persistence/recovery, or out-of-scope
future MVP milestone. Use those evidence-linked defects to decide the
smallest follow-up implementation. Do not infer an approved goal from
model text or a passing automated score.
