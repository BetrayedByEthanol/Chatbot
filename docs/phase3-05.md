# P3-05 — Outcome Evaluation & Safe Adaptation

**Authority:** Architecture v2.5.1 §§21.2–21.4, 22.1–22.3; P3-02 Task corrections, P3-03 immutable versioned methods, P3-04 durable runs and registered AGENT result fences.

## Boundaries

1. **Procedure Manager owns method evaluation.** `EvaluateProcedureRunCommand` records an authenticated, evidence-quoted user assessment and optional exact immutable step-event references. It is an **observation** (`UNKNOWN`, `INCOMPLETE`, `USER_REPORTED_SUCCESS`, `USER_REPORTED_FAILURE`) with confidence and documented diagnosis; it is **not** task completion, goal achievement, or independent verification.
2. **Success criteria are explicit.** A `USER_REPORTED_SUCCESS` assessment requires the run to be `USER_CONFIRMED`, every USER step to have `USER_CONFIRMED` evidence, every AGENT step to have `VERIFIED` P0 result evidence, and **every success criterion from its pinned shared template version** to have `USER_REPORTED_MET` testimony. Even this outcome is still a *reported* success, not external verification of the entire real-world result. Other outcomes may cite unmet or unknown criteria.
3. **Failure diagnosis is not automatic blame.** Reported failures distinguish `INCORRECT_INPUT`, `ENVIRONMENT`, `INCOMPLETE_USER_ACTION`, `METHOD_MISMATCH`, `INVALID_SUCCESS_CRITERIA`, and `UNDETERMINED`. A failure is not evidence that a shared procedure is universally ineffective. There is no automatic aggregate quality rating.
4. **Corrections append assessments.** `evaluation_revision` increments under an exclusive run row lock; every replacement explicitly identifies `expected_previous_evaluation_id`. The latest evaluation is the operative observation; historical assessments and cited step events remain immutable. One source user's assertion is not treated as independent corroboration of itself.
5. **Private-only adaptation proposals.** `ProposeProcedureAdaptationCommand` cites the latest negative/incomplete assessment of a run pinned to the **same currently active private variant revision** and pins the proposal's template/version, parameter values and allowed user instruction overrides. `STABLE` methods remain diagnostic-only; `PARAMETERIZED` methods can change validated parameters but not steps; `ADAPTIVE` methods may change up to four USER instructions using the existing P3-03 validation contract. Proposed content must differ from the current revision; a `PROPOSED` record does not alter the method.
6. **Approval owns publication to the private variant.** `DecideProcedureAdaptationCommand` requires an exact, separate action-bound user approval. `REJECT` preserves the method; `APPLY` checks that the proposal, evaluation, run evidence, selected goal strategy, private variant revision and template policy are still valid. It atomically appends an immutable private revision using the **existing** P3-03 `_save_variant_revision` code, advances only that variant's current revision and records an append-only decision. Already active runs remain pinned and unchanged.
7. **No shared promotion or goal mutation.** This PR neither publishes shared procedure definitions nor changes task outcomes, goal criteria, strategy selections, operation permissions, or scheduler admission. Shared promotion continues to require independent quality review and existing publisher permissions; no private experience leaks to another persona.

## Tables and failure behavior

`0020_procedure_evaluation.sql` adds scoped, immutable `procedure_run_evaluations`, `procedure_evaluation_step_evidence`, `procedure_evaluation_criteria`, `procedure_adaptation_proposals`, and `procedure_adaptation_decisions`. Composite foreign keys bind evaluations and proposals to the same User × Persona; history immutability triggers reject UPDATE/DELETE. The existing P3-03 command receipts provide idempotency, selected-persona generation fencing, authenticated source turns, approvals where consequential, event-stream provenance and transactional outbox. Optimistic run/variant/evaluation checks reject stale or conflicting proposals and decisions without partial changes.

`summarize_personal_procedure_experience` provides a bounded User × Persona view of the **latest evaluation per run** (including explicit unknown, incomplete, unevaluated and failure-cause counts), with truncation indicated and no global or independently verified effectiveness score. Reappraising the same run does not double-count it; the historical evaluation remains immutable. This is evidence aggregation for future selection, not automatic effectiveness optimization.

The effective procedure suitability indicator should remain a **derived future projection** rather than mutating P3-03's hard-coded `suitability_status='UNREVIEWED'` based on one sample. A longitudinal or cross-context success rate requires more evidence and safety review. P3-06 should verify multi-run effectiveness, correction consistency and state recovery without manufacturing extra confidence.

## Acceptance

`tests/test_phase3_learning.py` covers diagnostic categories, provenance/immutability, reported success criteria, no Goal/Task completion, safe parameterized and adaptive proposals, stable-procedure rejection, separate approval, no active run migration, proposal rejection, stale evaluation rejection, persona isolation and concurrent assessment revisions; and bounded cross-run aggregation that uses only the latest corrected evaluation per run without manufacturing a success rate. The full PostgreSQL/contract and real Ollama CI workflows must pass before review and merge.
